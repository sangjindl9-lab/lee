# 실행 · 배포

## 요구 사항

- Node.js 20 이상(개발·테스트는 22에서 확인)
- 영구 디스크 1개(`DATA_DIR`): SQLite DB(`eum.db`)와 암호화된 납품 파일(`files/`)이 저장됩니다
- 인스턴스 1개. SQLite와 메모리 기반 로그인 시도 제한을 쓰므로 여러 인스턴스로 늘리지 않습니다(확장 시 고려 사항은 아래)

## 환경변수

`.env.example`에 전체 목록과 설명이 있습니다. 운영에서 반드시 직접 정해야 하는 값:

| 변수 | 설명 |
|---|---|
| `NODE_ENV=production` | 운영 모드. 비밀값이 없으면 기동을 거부합니다 |
| `SESSION_SECRET`, `SANDBOX_WEBHOOK_SECRET` | `openssl rand -hex 32` |
| `FILE_MASTER_KEY` | 64자리 hex. 납품 파일과 계좌번호 암호화의 마스터 키. **분실하면 복호화할 수 없으므로 DB 백업과 다른 곳에 보관** |
| `BASE_URL`, `TRUST_PROXY=1`, `COOKIE_SECURE=1` | HTTPS 프록시 뒤에서 운영할 때 |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | 최초 최고관리자(없을 때만 생성). 첫 로그인 후 `/admin/mfa`에서 TOTP 등록 |
| `REQUIRE_ADMIN_MFA=1` | 운영 기본값. 운영자 화면은 TOTP 인증 후에만 열립니다 |
| `PAYMENT_PROVIDER` | `sandbox`(테스트) 또는 `toss`(미검증 어댑터, docs/05 참고) |
| `CLAMSCAN_PATH` | ClamAV 실행 파일 경로. 비우면 악성 파일 검사는 모든 파일에 "검사 불가"로 표시됩니다 |

## 로컬 실행

```bash
npm install
npm run seed                       # 선택
REQUIRE_ADMIN_MFA=0 npm start
```

DB 마이그레이션은 기동 시 자동 적용됩니다(`src/migrations/*.sql`, 적용 이력은 `schema_migrations`). 수동 실행은 `npm run migrate`.
스키마를 바꿀 때는 기존 파일을 고치지 말고 `002_*.sql`처럼 새 파일을 추가합니다.

## Docker

```bash
docker build -t eum-market .
docker run -d -p 3000:3000 -v eum-data:/data \
  -e SESSION_SECRET=... -e SANDBOX_WEBHOOK_SECRET=... -e FILE_MASTER_KEY=... \
  -e BASE_URL=https://example.com -e TRUST_PROXY=1 -e COOKIE_SECURE=1 \
  -e ADMIN_EMAIL=... -e ADMIN_PASSWORD=... eum-market
```

## Render

`render.yaml` 블루프린트를 사용할 수 있습니다. 디스크를 쓰려면 유료 요금제가 필요합니다. `FILE_MASTER_KEY`, `BASE_URL`, 관리자 계정은 배포 화면에서 직접 입력합니다.

## 주기 작업

서버 프로세스가 5분마다 다음을 실행합니다(`src/services/jobs.js`). 모두 여러 번 실행해도 안전합니다.

1. 파일 접근 실패 주문 복구 시도
2. 검수 기한 알림, 납품 지연 알림, (설정을 켠 경우에만) 자동확정
3. 처리 중 환불을 결제 사업자 조회로 확정
4. 접수·불명확 지급을 조회로 확정, 정산 주기에 맞춰 지급 요청
5. 대사(내부 상태 ↔ 사업자 상태 ↔ 원장)
6. 만료된 다운로드 링크·세션 정리

운영자는 `/admin`에서 수동 실행할 수 있습니다.

## 백업 · 복구

```bash
node scripts/backup.js /백업/경로      # 서비스 중 실행 가능, 무결성 검사 포함
```

- 백업 대상: `eum.db`(SQLite 온라인 백업)와 `files/`(암호화된 상태 그대로)
- `FILE_MASTER_KEY`는 백업에 들어 있지 않습니다. 별도 보관하세요
- 복구: 서버 중지 → 백업의 `eum.db`, `files/`를 `DATA_DIR`에 복사 → 같은 `FILE_MASTER_KEY`로 기동 → `/admin/reconcile`에서 대사 실행 → 파일 접근 실패 주문이 있으면 `/admin/orders?f=access_failed`에서 확인
- 권장: 매일 1회 이상 다른 저장소로 백업, 분기 1회 복구 연습

## 웹훅

결제 사업자 웹훅 주소는 `POST {BASE_URL}/webhooks/{provider}`입니다. 서명 검증에 실패하면 401을 돌려주고 아무것도 반영하지 않습니다.
웹훅이 유실돼도 대사 작업이 사업자에 결제 상태를 조회해 복구합니다.

## 보안 구성 요약

- 납품 파일: 웹 루트 밖 저장, 파일마다 AES-256-GCM 데이터 키, 데이터 키는 마스터 키로 감싸 DB에 저장, 키 ID 기록(교체 대비)
- 다운로드: 주문별 권한 확인 → 10분 만료·1회용·발급 계정 전용 링크 → 사용 시점 재확인 → 성공·거부 모두 기록
- 업로드: 용량 제한, 0바이트 거부, 압축 구조(항목 수·해제 용량·압축률·경로 탈출) 검사, 비밀키·환경변수·개인정보 패턴 검사, ClamAV 연동(선택). 업로드된 코드는 실행하지 않습니다
- 세션: HttpOnly·SameSite 쿠키, 서버 저장(토큰 해시), CSRF 토큰, 로그인 시도 제한, CSP·프레임 차단 헤더
- 운영자: 역할 분리, TOTP 추가 인증, 모든 변경 동작 감사 기록(수정·삭제 불가 트리거)
- 정산 계좌: 암호화 저장, 변경 시 비밀번호 재확인·알림·지급 보류

## 규모가 커질 때

- DB를 PostgreSQL로 옮기고(스키마는 표준 SQL에 가깝지만 부분 유일 인덱스·트리거 문법 이식 필요) 트랜잭션 격리 수준을 재검토
- 파일 저장소를 객체 저장소(서버 측 암호화 + 현재의 봉투 암호화 유지)로 이전
- 로그인 시도 제한과 주기 작업 잠금을 공유 저장소로 이전
- 마스터 키를 KMS로 이전
