# 이음마켓 거래 유형별 자금 흐름 · 납품물 흐름 설계

이 문서는 구현의 기준입니다. 코드(`src/services/*`)는 이 문서의 상태와 규칙을 그대로 따릅니다.

## 0. 세 가지를 분리한다

| 구분 | 누가 수행하는가 | 플랫폼이 하는 일 | 플랫폼이 하지 않는 일 |
|---|---|---|---|
| ① 결제대금 보호 | **결제 사업자(PG)** | PG에 결제·보류·지급을 요청하고 결과를 조회해 표시 | 플랫폼 DB의 "보류" 표시를 대금 보호라고 부르지 않음 |
| ② 납품물 보관 | **플랫폼** | 암호화된 비공개 저장소에 파일 보관, 주문별 접근 권한 발급 | 전문 소스코드 에스크로(제3자 임치) 계약과 같다고 표시하지 않음 |
| ③ 검수 후 정산 | **플랫폼 + PG** | 납품·검수·분쟁·환불·PG 지급 가능 상태를 모두 확인한 뒤 지급 요청 | 지급 "요청 접수"를 지급 "완료"로 표시하지 않음 |

주문 화면의 안전거래 표시는 주문마다 저장된 `protection_status` 값으로만 결정합니다.

| protection_status | 화면 표시 |
|---|---|
| `simulated` | 테스트 결제 — 실제 돈이 이동하지 않으며 대금 보호도 없습니다 |
| `held` | 결제 사업자가 대금을 보류 중(사업자 응답으로 확인됨) |
| `released` | 보류 해제됨 |
| `unsupported` | 이 결제에는 사업자 대금 보호가 적용되지 않습니다 |
| `unknown` | 사업자 상태 확인 중(확인 전에는 보호된다고 표시하지 않음) |

## 1. 주문의 7개 독립 상태

하나의 주문은 아래 상태를 **각각 따로** 가집니다(`orders` 테이블의 개별 컬럼).

| 컬럼 | 값 |
|---|---|
| payment_status | none → pending → paid → partially_refunded / refunded / failed / cancelled |
| protection_status | none / simulated / held / released / unsupported / unknown |
| delivery_status | not_ready / awaiting_seller / delivered / access_failed / redelivery_requested |
| inspection_status | not_started / in_progress / approved / auto_approved / closed_by_admin / rejected |
| dispute_status | none / open / resolved |
| refund_status | none / requested / processing / completed / failed / rejected / manual_required |
| payout_status | not_eligible / eligible / requested / unknown / paid / failed / held / clawback_review |

외부 사업자의 상태는 `payments.provider_status`, `protection_records`, `payouts.provider_status`에 따로 저장하고,
대사(`reconcile`)가 내부 상태와 비교해 불일치를 `reconciliation_issues`에 남깁니다.

## 2. A·B 완성형 상품(사용권 / 소스코드) — 즉시 납품

### 납품물 흐름

```
판매자: 상품 작성 → 파일 업로드(암호화 저장·해시·검사) → 버전 제출(이후 변경 불가)
운영자: 상품·파일 심사 → 승인 → 판매 시작
구매자: 주문 생성 시점에 [상품 설명·권리 조건·검수 기준·파일 목록과 해시·수수료 정책]을 스냅샷으로 고정
        결제 확인(서버가 PG 조회) → 주문 전용 접근 권한 발급 → 납품물 접근 가능 확인 → 검수 기간 시작
        다운로드(만료 링크, 매번 기록) → 설치·검수 → 구매확정 또는 문제 제기
```

규칙

- 판매 시작 전 실제 납품 파일이 등록·제출되어 있어야 승인 요청이 가능합니다. 소스 제공 상품은 `source` 역할 파일과 설치 설명서가 필수입니다.
- 제출된 버전의 파일 목록은 서비스 계층과 **DB 트리거** 양쪽에서 수정·삭제를 막습니다. 새 파일은 새 버전으로만 등록됩니다.
- 주문의 `version_id`, `snapshot_json`, `terms_hash`는 DB 트리거로 변경이 차단됩니다. 판매자가 상품을 업데이트해도 기존 주문 납품물은 그대로입니다.
- 접근 권한은 결제 상태를 **서버가 PG에 조회해 확인한 뒤** 발급합니다. 브라우저의 성공 화면이나 웹훅 본문만으로는 발급하지 않습니다.
- 구매확정은 파일 수령의 조건이 아닙니다. 다운로드와 구매확정은 별도 행위이며, 다운로드 기록만으로 검수 완료 처리하지 않습니다.
- 권한 발급 시 저장소에서 파일을 실제로 읽을 수 있는지 확인합니다. 실패하면 `delivery_status=access_failed`로 두고 **검수 기간을 시작하지 않으며**, 복구 작업이 성공한 시점부터 검수 기간을 셉니다.
- 판매자가 상품을 삭제하거나 탈퇴해도 파일과 버전은 보관 정책 기간(`retention_days`) 동안 유지되고 기존 주문의 접근 권한은 살아 있습니다.
- 파일 해시(SHA-256)는 "같은 파일인지" 확인하는 용도로만 표시합니다. 기능 작동이나 판매 권한의 증명이 아닙니다.

### 자금 흐름

```
구매자 ──결제──▶ 결제 사업자(PG)          [플랫폼은 돈을 직접 받지 않는 구조를 전제]
                  │ 보류(사업자가 지원하는 경우에만)
                  │
   (검수 승인 + 분쟁 없음 + 환불 없음 + 판매자 확인 + PG 지급 가능 + 중복 지급 아님)
                  ▼
플랫폼 ─지급 요청(멱등 키)─▶ PG ─지급─▶ 판매자 계좌
                                └ 플랫폼 수수료·결제 비용 차감
```

원장(`ledger_entries`, 주문 단위 복식 기록, 모든 거래 묶음의 합은 0)

| 사건 | 차변(+) | 대변(−) |
|---|---|---|
| 결제 확인 A | pg_holding A | seller_payable (A−수수료−판매자 부담 결제비용), platform_fee 수수료, pg_cost_passthrough |
| 환불 처리 시작 R | seller_payable·platform_fee 몫 | refund_in_transit R |
| 환불 완료 | refund_in_transit R | pg_holding R |
| 환불 실패 | (처리 시작의 역분개) | |
| 지급 요청 P | seller_payable P | payout_in_transit P |
| 지급 완료 | payout_in_transit P | pg_holding P |
| 지급 실패 | (지급 요청의 역분개) | |

`seller_payable` 잔액이 그 주문에서 쓸 수 있는 유일한 재원입니다. 환불과 지급은 같은 DB 트랜잭션 안에서
이 잔액을 먼저 차감(예약)한 뒤에만 외부 호출을 하므로, 동시에 실행돼도 같은 돈을 두 번 쓰지 못합니다.

## 3. C 맞춤 개발 — 단계별 거래

```
의뢰 등록 → 판매자 제안(범위·제외·단계·금액·검수 기준) → 구매자 선택
→ 계약 버전 1 (양측 동의, 조건 해시 고정)
→ 단계마다:  [단계 주문 생성 → 단계 결제 확인] → 작업 → 납품(파일) → 검수 → 승인/수정 요청 → 정산 조건 확인
```

- 단계별 결제는 "임의 분할 지급"이 아니라 **단계마다 별도의 주문·결제**입니다. 사업자 기능 확인표에서 '단계별 결제'가 확인되지 않으면 단계 결제 버튼이 비활성화되고 대체 절차(단일 결제)만 안내합니다.
- 해당 단계의 결제가 확인되기 전에는 "작업 시작" 상태로 넘어가지 않습니다.
- 소스 인도가 필요한 단계(`requires_source`)는 `source` 역할 파일과 실행 방법 문서가 납품에 포함돼야 납품 완료로 받아들입니다. 화면 캡처·영상만으로는 완료 처리되지 않습니다.
- 빈 파일(0바이트)은 업로드 단계에서 거부합니다.
- 수정 요청은 `계약 범위 내 / 범위 외 / 미분류`로 분류합니다. 범위 외 요청은 **변경 계약**(새 계약 버전, 기존 범위와 추가 범위를 나란히 표시, 금액·기간 변경에 양측 동의)으로만 반영됩니다.

자금 흐름은 2절과 같고 단계 주문마다 독립적으로 적용됩니다.

## 4. D 지식재산권 거래

```
상담 → 비밀유지 조건 합의(양측 동의 기록) → 권리자가 열람 승인 → 비공개 자료실 열람(열람 기록)
→ 권리·기술 확인 → 거래 조건 확정 → 계약(초안 표시) 및 결제 → 자산 인도 목록 항목별 인도·확인
→ 필요한 권리 이전 절차 확인 → 완료 → 정산
```

- 사용권 구매 / 소스 인도 / 권리 양도는 서로 다른 거래 유형으로 저장·표시합니다. 소스 파일 전달은 권리 이전을 뜻하지 않습니다.
- 독점 거래(양도·독점 이용허락)는 조건 확정 시점에 매물에 잠금을 걸어 다른 거래의 진행을 막습니다. 거래가 취소되면 잠금이 풀립니다.
- 인도 항목은 유형별로 "판매자 인도 표시 + 구매자 수령 확인"이 모두 있어야 완료됩니다. 서비스 계정·앱 등록 자산은 제공자의 공식 이전 절차 확인 메모가 필요하며, 비밀번호 전달은 완료 근거가 아닙니다.
- 모든 항목과 권리 이전 절차 확인이 끝나야 검수 승인 → 정산 조건 확인으로 넘어갑니다.
- 플랫폼이 제공하는 계약서는 법률 검토 전 **초안**으로 표시합니다.

## 5. 분쟁 · 환불 · 사후 회수

```
문제 접수 → (정산 내부 보류) + (PG 지급 보류 요청 → 결과를 따로 기록: 확인됨 / 실패 / 미지원)
→ 양측 자료 제출 → 수정·합의 제안 → 운영자 결정(근거·처리자·일시 기록) 또는 외부 절차 안내
→ 환불 / 거래 재개 / 정산
```

- 환불 요청(`requested`) → 처리 중(`processing`) → **PG 취소 성공 확인 후** 완료(`completed`).
- 결제수단이 부분 취소를 지원하지 않으면 `manual_required`로 두고 대체 절차를 안내합니다.
- 이미 지급된 거래는 일반 보류로 되돌릴 수 없으므로 `payout_status=clawback_review`(사후 환불·회수 검토)로 연결합니다.
- 환불 완료 후: 추가 다운로드 차단, 이용 종료 안내, 구매자의 삭제·이용중단 확인. 이미 받은 파일의 원격 삭제는 불가능하며 화면에 그대로 표시합니다.
- 운영자 결정 후 이의제기 기간(`appeal_days`) 동안은 판매자 지급을 보류합니다.
- AI 기능은 초안 작성 보조에만 쓰이고 환불·권리 분쟁 결정 경로에는 연결돼 있지 않습니다.

## 6. 결제 사업자 기능 확인표와 기능 활성화

`pg_capability_checks`에 항목별 확인 결과(확인자·일시·근거)를 기록합니다. 확인되지 않은 항목에 의존하는 기능은 꺼집니다.

| 항목 | 미확인 시 동작 |
|---|---|
| 디지털 상품·개발 용역 취급, 다수 판매자 구조 | 실결제 모드 전환 불가 |
| 최대 보류 기간·자동확정 방식 | (납품 기한 + 검수 기간 + 분쟁 여유일)이 보류 기간을 넘는 상품은 결제 차단 |
| 분쟁 시 지급 중지 | 분쟁 화면에 "외부 보류 미지원 — 내부 정산만 보류" 표시 |
| 부분 환불 | 부분 환불은 수동 절차로 전환 |
| 단계별 결제 | 단계 결제 비활성화 |
| 판매자 확인·지급 API | 자동 지급 대신 수동 지급 기록 절차 |
| 지급 후 환불 | 사후 회수 검토 절차만 제공 |

## 7. 동시성 · 멱등성

- 웹훅: 공식 서명 검증 → `webhook_events.event_id` 유일 제약으로 중복 제거 → 본문을 믿지 않고 PG에 현재 상태를 조회해 반영. 따라서 지연·역순 도착에도 최종 상태가 같습니다.
- 지급: `payouts.idempotency_key` 유일, 주문당 진행 중 지급 1건(부분 유일 인덱스). 응답이 불명확하면 `unknown`으로 두고 조회 후 같은 키로만 재시도합니다.
- 환불: `refunds.idempotency_key` 유일. 완료 전까지 금액은 `refund_in_transit`에 묶입니다.
