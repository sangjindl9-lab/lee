# 7대 상태 전이 규칙 · 금액/세무 원장 로직

구현 위치: `src/services/*`. 여기 적힌 전이 외의 변경 경로는 코드에 없습니다.
요구사항의 `escrow_status`는 이 구현에서 `orders.protection_status` 컬럼입니다(이름만 다르고 의미는 같습니다).

## 1. 상태 전이 규칙

### ① 결제 상태 `payment_status`

| 전이 | 조건 | 실행 주체 |
|---|---|---|
| none → pending | 구매자가 결제 시작, 일정 충돌 검사 통과 | `orders.startPayment` |
| pending → paid | **서버가 사업자에 조회한 결과**가 결제 완료이고 금액이 주문과 같음 | `orders.syncPayment` (웹훅·복귀 화면·대사가 호출) |
| pending → failed | 사업자 조회 결과 실패 | 〃 |
| paid → partially_refunded / refunded | 환불이 **완료**(사업자 취소 확인)됨 | `refunds.finalize` |
| failed·cancelled → pending | 구매자가 다시 결제 시작 | `orders.startPayment` |

금지: 브라우저 복귀 화면이나 웹훅 본문만으로 paid 처리. 금액이 다르면 paid가 되지 않고 대사 문제로 기록됩니다.

### ② 대금 보호 상태 `protection_status` (= escrow_status)

| 값 | 설정 시점 | 근거 |
|---|---|---|
| none | 결제 전 | — |
| simulated | 결제 확인, 테스트 사업자 | 실제 보호 없음 |
| held | 결제 확인, 사업자가 보류 중이라고 응답 | 사업자 응답 |
| unsupported | 결제 확인, 사업자가 보류를 제공하지 않음 | 사업자 응답 |
| unknown | 사업자 응답으로 판단 불가 | — |
| held → released | 판매자 지급 완료 확인 | `settlement.finalizePaid` |

내부 정산 보류(`payout_status=held`)는 이 상태를 바꾸지 않습니다. 분쟁 시 사업자 보류 요청 결과는 `disputes.external_hold`에 따로 기록합니다.

### ③ 납품 상태 `delivery_status`

| 전이 | 조건 |
|---|---|
| not_ready → delivered | (완성형) 결제 확인 + 주문에 고정된 파일을 저장소에서 실제로 읽을 수 있고 해시가 일치 |
| not_ready → access_failed | (완성형) 결제 확인됐지만 파일을 읽을 수 없음 → 복구 작업이 성공하면 delivered |
| not_ready → awaiting_seller | (맞춤 개발 단계·권리 거래) 결제 확인. 납품 기한 = 결제 확인 + 약정 일수 |
| awaiting_seller·redelivery_requested → delivered | 판매자 납품 제출이 누락 검사 통과(필수 파일, 소스 단계는 소스+실행 방법, 문제 파일 없음) / 권리 거래는 인도 항목 전부 인도 표시 |
| delivered → redelivery_requested | 판매자가 수정 요청을 "계약 범위 내"로 수락(재납품이 필요한 거래) |

### ④ 검수 상태 `inspection_status`

| 전이 | 조건 |
|---|---|
| not_started → in_progress | 납품 상태가 delivered가 된 시점. 기한 = 그 시점 + 주문에 고정된 검수 일수 |
| in_progress → approved | 구매자(또는 구매 기업의 검수 담당자) 구매확정. 분쟁·환불 진행 중이 아님, 설치 지원 포함 시 설치 완료 확인, 권리 거래는 인도·권리 이전 절차 확인 완료 |
| in_progress → auto_approved | 기한 경과 + 자동확정 설정 켜짐 + 열린 수정 요청 없음 + 권리 거래·별도 확인 거래 아님 |
| in_progress → closed_by_admin | 기한 경과 후 운영자 검수 종료(근거 필수) 또는 분쟁 결정 |
| in_progress → not_started | 재납품 대기로 전환(기한 정지) |
| (분쟁 "거래 재개") → in_progress | 새 기한 부여 |

금지: 납품 상태가 delivered가 아닌 주문의 검수 시작·구매확정. 다운로드 사실로 인한 전이는 없습니다.

### ⑤ 분쟁 상태 `dispute_status`

| 전이 | 조건 |
|---|---|
| none·resolved → open | 당사자가 문제 제기(결제 확인된 주문, 진행 중 분쟁 없음) 또는 이의제기 |
| open → resolved | 양측 합의(상대방의 제안 수락) 또는 운영자 결정(근거 필수, 처리자·일시 기록) |
| open 유지 | "외부 해결 절차 안내" 결정(자금은 계속 보류) |

분쟁 시작 시: `payout_status` → held(지급 전) / clawback_review(지급 후), 사업자 지급 보류 요청 → confirmed / failed / unsupported / not_applicable.

### ⑥ 환불 상태 `refund_status`

| 전이 | 조건 |
|---|---|
| none → requested | 구매자가 분쟁에서 환불을 요청 |
| requested → rejected | 분쟁이 환불 아닌 결과로 종결 |
| → processing | 환불 실행: 원장에서 금액을 먼저 묶고 사업자 취소 요청 |
| processing → completed | **사업자 조회로 취소 금액 반영이 확인됨** |
| processing → failed | 사업자가 명확히 거절(묶은 금액 환원). 응답 불명확은 processing 유지 후 조회 |
| → manual_required | 결제수단이 부분 취소 미지원 / 이미 판매자에게 지급된 거래 |
| manual_required → completed·rejected | 운영자가 수동 처리 결과와 증빙 기록 |

### ⑦ 판매자 지급 상태 `payout_status`

| 전이 | 조건 |
|---|---|
| not_eligible ↔ eligible | 지급 차단 사유 목록(`settlement.blockers`)이 비면 eligible |
| → held | 분쟁 진행 또는 환불 요청·처리 중 |
| eligible → requested | 한 트랜잭션에서 조건 재확인 + 금액 예약 + 지급 행 생성(주문당 진행 중 1건) |
| requested → paid | 사업자 조회 결과 지급 완료 |
| requested → unknown | 응답 불명확(타임아웃) → 조회로 확정, 사업자에 기록이 없을 때만 같은 멱등 키로 재요청 |
| requested·unknown → failed | 사업자가 명확히 실패 응답(예약 환원) → 조건이 맞으면 다시 eligible |
| paid → clawback_review | 지급 후 분쟁·환불 결정 |

지급 차단 사유: 결제 미확인, 미납품, 검수 미종료, 분쟁 중, 환불 진행 중, 별도 확인 미완료, 이의제기 기간, 판매자 승인 상태, 정산 계좌 없음·변경 보류 중, 진행 중·완료된 지급 존재, 지급할 금액 없음.

## 2. 금액 계산

모든 금액은 원 단위 정수입니다. 소수 연산을 저장하지 않습니다.

| 항목 | 계산 | 고정 시점 |
|---|---|---|
| 플랫폼 수수료 | `floor(결제액 × 수수료율(bps) ÷ 10000)`. 수수료율은 판매자별 > 카테고리별 > 기본, 같은 범위에서는 기간 한정 정책 우선 | 주문 생성 시 주문에 저장(DB 트리거로 변경 차단) |
| 수수료 부가세 | 부가세 포함 설정이면 `floor(수수료 ÷ 11)`, 공급가액 = 수수료 − 부가세 | 주문 생성 시 |
| 결제 비용 | `floor(결제액 × 결제 비용률 ÷ 10000)` — 추정치. 부담 주체가 판매자면 정산 대상액에서 차감 | 주문 생성 시 |
| 정산 대상액 | 결제액 − 수수료 − (판매자 부담 결제 비용) − 환불 중 판매자 몫 | 원장 `seller_payable` 잔액 |
| 부분 환불 | 환불 후 남는 거래액으로 수수료를 다시 계산해 차액을 수수료 환원, 나머지를 판매자 몫에서 차감 | 환불 실행 시 |
| 원천징수 | 개인 판매자만. 소득세 = `floor(정산 대상액 × 3%)`의 10원 미만 절사, 지방소득세 = `floor(소득세 × 10%)`의 10원 미만 절사 | 지급 요청 시(지급액 기준) |
| 실제 지급액 | 정산 대상액 − 원천징수 세액 | 지급 요청 시 `payouts.amount` |

예: 결제 500,000원, 수수료 10%, 개인 판매자
→ 수수료 50,000(공급가액 45,455 + 부가세 4,545) / 정산 대상액 450,000 / 소득세 13,500 + 지방소득세 1,350 / 실제 지급 435,150

## 3. 판매자 과세 유형별 처리 (`src/services/tax.js`)

| 과세 유형 | 지급 시 공제 | 지급 완료 시 생성되는 증빙 기초 데이터(`tax_records`) |
|---|---|---|
| 법인·일반과세자 `general` | 없음 | `fee_tax_invoice`: 수수료 공급가액 + 부가세 10% |
| 간이과세자 `simplified` | 없음 | 세금계산서 수수 대상이면 `fee_tax_invoice`, 아니면 `fee_record`(정산 내역 기록) |
| 개인(비사업자) `individual` | 사업소득 3.3% 원천징수 | `withholding`: 지급 대상액·소득세·지방소득세·귀속 연월(지급명세서 기초) + `fee_record` |

- 과세 유형은 판매자 승인 전에는 본인이 선택하고, 승인 후에는 운영자가 확인 근거와 함께만 바꿀 수 있습니다(감사 기록).
- 지급 시점의 과세 유형이 지급 행(`payouts.tax_type`)에 기록됩니다.
- 운영자 화면 `/admin/tax`에서 귀속 연월별 조회, 합계, CSV 내보내기, 처리 참조 기록을 할 수 있습니다.
- **범위 밖**: 실제 세금계산서 발행, 원천세 신고·납부, 지급명세서 제출, 소득자 식별정보(주민등록번호 등) 수집. 세율·절사·소액부징수 기준과 "플랫폼이 원천징수 의무자인지"는 세무 검토가 필요합니다.

## 4. 원장 (`ledger_entries`)

주문 단위 복식 기록. 차변 +, 대변 −, 한 묶음(`txn`)의 합은 항상 0이며 수정·삭제할 수 없습니다(DB 트리거).

| 계정 | 의미 |
|---|---|
| pg_holding | 결제 사업자에 있는 이 주문의 돈 |
| seller_payable | 판매자에게 지급할 금액(정산 대상액) |
| platform_fee | 플랫폼 수수료 수익(부가세 포함) |
| pg_cost_passthrough | 판매자 부담 결제 비용 |
| refund_in_transit | 처리 중인 환불 |
| payout_in_transit | 처리 중인 지급 |
| withholding_payable | 원천징수 예수금(세무서 납부 대상) |

| 사건 | 분개 |
|---|---|
| 결제 확인 A | pg_holding +A / seller_payable −(A−수수료−결제비용) / platform_fee −수수료 / pg_cost_passthrough −결제비용 |
| 환불 처리 시작 R | seller_payable +판매자몫 / platform_fee +수수료환원 / pg_cost_passthrough +결제비용환원 / refund_in_transit −R |
| 환불 완료 | refund_in_transit +R / pg_holding −R |
| 환불 실패 | 처리 시작의 역분개 |
| 지급 요청 (대상액 G, 원천징수 W) | seller_payable +G / payout_in_transit −(G−W) / withholding_payable −W |
| 지급 완료 | payout_in_transit +(G−W) / pg_holding −(G−W) |
| 지급 실패 | 지급 요청의 역분개 |

대사가 매번 확인하는 불변식

1. 모든 묶음의 합 = 0
2. `seller_payable` 잔액 ≥ 0
3. `pg_holding` 잔액 = 결제액 − 환불 완료액 − 지급 완료액 (남는 금액 = 수수료 + 원천징수 예수금 + 미지급 정산 대상액)
4. 사업자의 결제 금액·환불액·지급액 = 내부 기록

## 5. 경쟁 조건 차단

- 환불과 지급은 모두 "즉시 잠금 트랜잭션(BEGIN IMMEDIATE) 안에서 조건 확인 → `seller_payable` 차감 → 행 생성"을 먼저 끝낸 뒤에만 사업자를 호출합니다. 먼저 잠금을 잡은 쪽이 금액을 가져가고 다른 쪽은 조건 검사에서 거절됩니다.
- 유일 제약: 주문당 진행 중·완료 지급 1건, 진행 중 환불 1건, 지급·환불 멱등 키, 웹훅 이벤트 ID.
